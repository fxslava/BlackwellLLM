# ============================================================================
# MSVC toolset pin (opt-in; empty = off). BEFORE project(), because it has to be
# in place before the compiler is detected.
#
# WHY THIS EXISTS. MSBuild does not use "the newest toolset installed" -- for
# PlatformToolset v143 it uses whatever
# VC/Auxiliary/Build/Microsoft.VCToolsVersion.v143.default.txt names, which on a
# VS 2022 install that has not been updated in a while can be years older than
# the compilers sitting next to it. That is invisible until a PREBUILT static
# library (here: vcpkg's WebRTC) calls an STL entry point the older CRT does not
# export, and then it is LNK2001 on __std_* symbols nobody in this repo wrote,
# at the end of a very long link. cmake/WebRtcAec3.cmake checks for exactly that
# and refuses to configure rather than let the build get that far.
#
# HOW, and why it is Directory.Build.props rather than the two obvious options.
# All three were measured on a VS 17.13 install whose v143 default is 14.34:
#
#   -T version=<x.y.z>  (CMAKE_GENERATOR_TOOLSET)  -- DOES NOT WORK. CMake accepts
#       it and writes no <VCToolsVersion> into the .vcxproj at all, so MSBuild
#       resolves v143 through its default file and compiles with the old toolset.
#   CMAKE_VS_GLOBALS "VCToolsVersion=..."          -- DOES NOT WORK. The property
#       lands in the Globals group ahead of the Microsoft.Cpp.Default.props
#       import whose own assignment is guarded by Condition="'$(VCToolsVersion)'
#       == ''", i.e. exactly where it ought to win -- and MSBuild honours the
#       default file regardless.
#   Directory.Build.props in the BINARY DIR                -- WORKS, and is what
#       this uses. MSBuild imports it from Microsoft.Common.props, before the C++
#       toolset is resolved, and it is found by walking up from each .vcxproj --
#       so one file at the top of the build tree covers every project in it.
#
# IT WORKS FROM THE IDE TOO, which is the point: Ctrl+Shift+B picks it up with no
# command line, no vcvars wrapper and no build preset. That is what a .sln in
# out/build/ needs in order to be self-contained.
#
# Still not a substitute for repairing the VS installation -- it pins THIS tree,
# not the machine. A machine-specific value, so it belongs in
# CMakeUserPresets.json alongside VCPKG_ROOT, not in the committed presets.
#
#   cmake --preset x64-release-aec3 -D BLACKWELL_MSVC_TOOLSET_PIN=14.43.34808
# ============================================================================
set(BLACKWELL_MSVC_TOOLSET_PIN "" CACHE STRING
    "MSVC toolset version MSBuild must use for this build tree (e.g. 14.43.34808). Empty = MSBuild's v143 default.")
if(BLACKWELL_MSVC_TOOLSET_PIN)
    # Written unconditionally on every configure so the file cannot drift from
    # the cache value that documents it.
    file(WRITE "${CMAKE_BINARY_DIR}/Directory.Build.props"
"<Project>\n"
"  <!-- GENERATED by the root CMakeLists from BLACKWELL_MSVC_TOOLSET_PIN.\n"
"       Do not edit; re-run CMake to change it. Pins the MSVC toolset for every\n"
"       project in this build tree, including builds started from the IDE. -->\n"
"  <PropertyGroup>\n"
"    <VCToolsVersion>${BLACKWELL_MSVC_TOOLSET_PIN}</VCToolsVersion>\n"
"  </PropertyGroup>\n"
"</Project>\n")
    message(STATUS "MSVC toolset pin: ${BLACKWELL_MSVC_TOOLSET_PIN} (via ${CMAKE_BINARY_DIR}/Directory.Build.props)")
endif()

# ============================================================================
# Static CRT (/MT, /MTd) -- enterprise-grade, dependency-free deployment.
# Set BEFORE any target or FetchContent dependency so googletest/nlohmann and
# every first-party target link the SAME runtime (a /MT<->/MD mismatch is a hard
# LNK2038). CMP0091 (NEW under cmake>=3.28) routes this through the abstract
# MSVC_RUNTIME_LIBRARY property instead of hand-patched CMAKE_*_FLAGS.
#
# Safe across the SHARED blackwell_core.dll boundary: the COM edge passes only
# HRESULTs + POD across the DLL seam (no CRT objects -- FILE*, malloc'd blocks,
# or C++ exceptions -- ever cross it), so the exe and the DLL each owning a
# private static CRT copy is by design (see the hybrid error doctrine).
# ============================================================================
set(CMAKE_MSVC_RUNTIME_LIBRARY "MultiThreaded$<$<CONFIG:Debug>:Debug>")

# ============================================================================
# CUDA AOT fatbinary matrix (deployment target coverage).
#   <arch>-real    -> native SASS baked into the fatbinary for that GPU.
#   <arch>-virtual -> PTX kept for forward JIT onto any newer, unlisted arch.
# Turing..Hopper get native SASS; 90-virtual PTX JITs forward onto future parts.
# 120-real is the project's PRIMARY target (Blackwell / RTX 50xx) -- keep native
# SASS so the latency-critical hot path never pays a first-launch PTX-JIT stall
# on the very hardware this engine exists for. (Drop 120-real ONLY for a build
# that will never run on Blackwell; the 90-virtual PTX would then cover it.)
#
# GUARDED so the CMakePresets cache var wins: the x64-release preset pins THIS
# matrix, while x64-debug stays single-arch (fast local iteration). This block is
# the fallback for a raw, preset-less `cmake -S . -B ...` and the canonical record
# of the shipping matrix. Keep it in lock-step with the release preset's
# CMAKE_CUDA_ARCHITECTURES.
#
# TEMPORARILY single-arch (120-real only): the current kernels use Blackwell/
# Hopper-specific instructions (sm_90+ intrinsics -- e.g. TMA / wgmma / cluster
# ops) that do NOT compile for older SASS, so building 75/86/89 fails outright.
# The broader matrix below is the INTENDED deployment target once those kernels
# grow pre-sm_90 fallbacks; re-enable arch-by-arch as each is ported and its
# build goes green. See the deployment matrix in deploy/README.md.
if(NOT DEFINED CMAKE_CUDA_ARCHITECTURES)
    set(CMAKE_CUDA_ARCHITECTURES
        # --- intended future deployment matrix (disabled: pre-sm_90 kernels do
        #     not yet compile -- Blackwell/Hopper-only intrinsics in use) ---
        # 75-real       # Turing   (RTX 20xx / GTX 16xx)
        # 86-real       # Ampere   (RTX 30xx, A-series)
        # 89-real       # Ada      (RTX 40xx)
        # 90-real       # Hopper   (H100 / H200)
        # 90-virtual    # PTX fallback: forward-compatible JIT for any arch > sm_90
        120-real      # Blackwell (RTX 50xx) -- primary target, native SASS
    )
endif()

# ============================================================================
# Compiler hygiene: zero-warning policy on our first-party CXX code.
# Placed AFTER the dependency includes so already-defined FetchContent targets
# (googletest, ...) keep their own warning level -- this directory property
# only applies to targets created below (src/, tests/).
#   - CXX only: nvcc host-passthrough of /W4 /WX over CUDA/CCCL headers is not
#     viable, so CUDA (.cu) compilation is untouched.
#   - /external:anglebrackets + /external:W0: <>-includes (CUDA toolkit, STL,
#     Win32, deps) are "external" and drop to W0, so /W4 /WX fires ONLY on our
#     own "..."-included code.
# ============================================================================
if(MSVC)
    add_compile_options(
        "$<$<COMPILE_LANGUAGE:CXX>:/W4>"
        "$<$<COMPILE_LANGUAGE:CXX>:/WX>"
        "$<$<COMPILE_LANGUAGE:CXX>:/external:anglebrackets>"
        "$<$<COMPILE_LANGUAGE:CXX>:/external:W0>"
        # C4996 deprecates STANDARD C functions (getenv/fopen/...) in favour of
        # MSVC's non-portable *_s variants. This code is cross-platform-standard,
        # so silence that one non-warning (CXX only -- CUDA TUs are untouched, so
        # they never recompile for it) rather than un-portably rewriting it.
        "$<$<COMPILE_LANGUAGE:CXX>:/D_CRT_SECURE_NO_WARNINGS>"
    )

    # THE CUDA COUNTERPART TO /external:W0, and it exists for the same reason:
    # a diagnostic about code nobody here wrote.
    #
    # nvcc compiles each .cu in two passes and emits a C stub
    # (%TEMP%/tmpxft_*.cudafe1.stub.c) between them, which the host compiler then
    # builds. That generated stub declares a kernel entry extern and defines it
    # static, and cl reports C4211 "nonstandard extension used: redefined extern
    # to static" -- pointing at a temp file that does not survive the build and
    # that no edit in this repo can change. Currently one site
    # (src/bridge/prompt_injector.cu); suppressed project-wide rather than at
    # that target because the trigger belongs to nvcc's codegen, not to the file.
    #
    # -Xcompiler, not a bare /wd: this must reach the HOST compiler nvcc drives,
    # and it is scoped to CUDA TUs, so first-party C++ keeps the full /W4 /WX.
    add_compile_options("$<$<COMPILE_LANGUAGE:CUDA>:-Xcompiler=/wd4211>")
endif()

# ============================================================================
# Release optimization profile (enterprise build).
# Generator-expression gated on $<CONFIG:Release> so Debug/RelWithDebInfo are
# untouched. NDEBUG + the Release CRT flags come from CMake's own
# CMAKE_*_FLAGS_RELEASE; this block adds the AGGRESSIVE layer on top.
#   CXX  : /O2 max speed, /Oi intrinsics, /Ot favor speed, /GL whole-program opt,
#          /Gy COMDAT sections (feeds /OPT:ICF). Aggressive inlining (/Ob3) is
#          SUBSTITUTED into CMAKE_CXX_FLAGS_RELEASE rather than appended here --
#          see the string(REPLACE) below for why that is not a style choice.
#   LINK : /LTCG cross-module codegen (pairs with /GL), /OPT:REF strips unused
#          code+data, /OPT:ICF folds identical COMDATs, /INCREMENTAL:NO (LTCG is
#          incompatible with incremental linking).
#   CUDA : /GL is deliberately NOT forwarded through nvcc (host-passthrough LTCG
#          is unsupported); device code is tuned via ptxas -O3 instead. Mixed
#          /GL (CXX) + non-/GL (CUDA) objects link cleanly -- LTCG applies to the
#          /GL subset only.
# ============================================================================
if(MSVC)
    # /Ob3 IS A REPLACEMENT, NOT AN ADDITION -- and that distinction is the whole
    # reason this line exists rather than another entry in the list below.
    # CMake's own CMAKE_CXX_FLAGS_RELEASE already carries "/O2 /Ob2 /DNDEBUG", so
    # appending /Ob3 put both inlining levels on the same command line and cl
    # answered with `command line warning D9025: overriding '/Ob2' with '/Ob3'`
    # -- once per Release C++ TU, 214 times in a full build. The flag WORKED (the
    # later one wins); it just buried real diagnostics under a warning the build
    # generated against itself. Substituting in place asks for /Ob3 exactly once.
    #
    # SCOPE: this is a normal variable shadowing the cache entry, so it reaches
    # the subdirectories added BELOW (src/, tests/, audio_sandbox/) and not the
    # FetchContent targets configured further up -- googletest and ImGui keep
    # plain /Ob2, which is what they had before and warns about nothing.
    string(REPLACE "/Ob2" "/Ob3" CMAKE_CXX_FLAGS_RELEASE "${CMAKE_CXX_FLAGS_RELEASE}")

    add_compile_options(
        "$<$<AND:$<COMPILE_LANGUAGE:CXX>,$<CONFIG:Release>>:/O2>"
        "$<$<AND:$<COMPILE_LANGUAGE:CXX>,$<CONFIG:Release>>:/Oi>"
        "$<$<AND:$<COMPILE_LANGUAGE:CXX>,$<CONFIG:Release>>:/Ot>"
        "$<$<AND:$<COMPILE_LANGUAGE:CXX>,$<CONFIG:Release>>:/GL>"
        "$<$<AND:$<COMPILE_LANGUAGE:CXX>,$<CONFIG:Release>>:/Gy>"
        # Device-side optimization for the CUDA translation units.
        "$<$<AND:$<COMPILE_LANGUAGE:CUDA>,$<CONFIG:Release>>:-O3>"
        "$<$<AND:$<COMPILE_LANGUAGE:CUDA>,$<CONFIG:Release>>:-Xptxas=-O3>"
    )
    add_link_options(
        "$<$<CONFIG:Release>:/LTCG>"
        "$<$<CONFIG:Release>:/OPT:REF>"
        "$<$<CONFIG:Release>:/OPT:ICF>"
        "$<$<CONFIG:Release>:/INCREMENTAL:NO>"
    )
endif()

# ============================================================================
# Solution-folder assignments (USE_FOLDERS is ON above). Centralised here --
# after every add_subdirectory -- so all targets exist and the taxonomy lives in
# one readable place instead of scattered set_target_properties calls. Each is
# guarded by if(TARGET ...) because most subdirectories are option-gated.
# ============================================================================
function(blackwell_set_folder folder)
    foreach(tgt ${ARGN})
        if(TARGET ${tgt})
            set_target_properties(${tgt} PROPERTIES FOLDER "${folder}")
        endif()
    endforeach()
endfunction()

# The taxonomy is FUNCTIONAL, not physical: it groups targets by the job they do
# in the running product, which is not always where their sources live. Libraries
# sit under their domain, executables under Apps -- so "what is this code for?"
# and "what can I run?" are two different questions with two different answers.
#
# NOTHING HERE MOVES A FILE. The on-disk layout (src/core = the CUDA engine,
# src/audio = CUDA audio, src/audio_rt = the dependency-free RT primitives) is
# unchanged and still matches CLAUDE.md's project map. This is a view.
#
# TWO THINGS THIS VIEW CANNOT EXPRESS, both because folders group TARGETS:
#   * WASAPI has no folder. audio_capture.cpp / audio_playback.cpp are compiled
#     directly into each app executable rather than into a library of their own,
#     so they appear under whichever app pulls them in.
#   * There is no Util domain. The lock-free queue (spsc_ring.hpp) ships inside
#     blackwell_audio_rt; giving it a folder of its own would mean splitting it
#     into its own target first -- a physical change, deliberately not made here.
